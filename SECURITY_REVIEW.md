# Security Review — PsychAid

## Verdict

PsychAid should not yet be shipped to clinicians as-is. The loopback-only design and in-memory report handling substantially reduce exposure, and no real provider credential was found in the working tree or git history. However, an uploaded filename can execute JavaScript in the trusted app origin, and the release build executes unpinned dependencies while holding repository write authority. The remaining issues are mostly medium or low impact under this local-desktop threat model, but the two High findings should be fixed before distribution. The full pytest suite was not runnable in this review environment because the repository dependencies and pytest are not installed; targeted dependency-free/Flask-stub checks are identified explicitly below.

On a platform that permits HTML metacharacters in filenames, a patient can supply a file named like an HTML element with an event handler. When the clinician selects it, the handler runs in the PsychAid origin. It can read the global `fileList` `File` objects and send the selected clinical documents to an external host, as well as call the unauthenticated local APIs. ## Not a problem

- **Saved keys are not rendered by the settings page.** `app.py:31-50` constructs `public_settings` without `api_keys` and exposes only per-provider booleans. The existing test at `test_psychaid.py:239-248` asserts that a saved sentinel credential is absent from the response.
- **Subscription mode does not fall back to a stored key.** `providers.py:154-169` reads only the selected provider's environment variable in subscription mode. A direct execution check with a stored sentinel and an absent environment variable produced the named missing-environment error rather than returning the stored key.
- **Provider errors redact a directly embedded key.** `providers.py:12-16`, `providers.py:37-41`, `providers.py:86-102` route Anthropic and Gemini error details through the same exact-substring replacement. Direct checks of the Anthropic path and the existing Gemini test at `test_psychaid.py:165-187` showed the sentinel removed. This is why SEC-08 is Low rather than a credential-leak finding.
- **The API key is not supplied to the model as prompt text and is not added to DOCX/PDF output.** `report_generator.py:94-101` passes it as the provider authentication argument, separate from document text; `report_generator.py:104-139` and `pdf_forms.py:7-99` construct output only from report/form content and the client name.
- **Patient data is not written to an application database or temp file.** `database.py:1-8` only defines/creates an otherwise unused directory, and `init_db` has no caller. Uploaded files, generated DOCX, and PDFs stay in `BytesIO`/memory (`app.py:102-120`, `report_generator.py:136-139`, `pdf_forms.py:8-9`, `pdf_forms.py:97-99`). A final report/form persists only where the browser or native save dialog places it (`main.py:39-51`). The mismatch between `database._data_dir` and `report_generator._config_path` therefore does not currently split patient records across locations.
- **The hardcoded Flask secret currently has no security effect.** `app.py:14` is weak, but no route uses Flask `session`, signed cookies, or flash messages. Remove it until needed or generate a random secret before introducing session state.
- **The shipped entry point disables debug and the reloader.** `main.py:19-21` sets `debug=False` and `use_reloader=False`; the source-only fallback at `app.py:143-144` also sets `debug=False`. No environment/config path in this repository turns debug on.
- **Loopback binding is real.** Both entry points bind `127.0.0.1` (`main.py:11`, `main.py:21`, `app.py:144`), so the Flask service is not directly reachable from another machine. This substantially lowers the severity of SEC-04, SEC-06, SEC-08, and SEC-09.
- **No credential was found in the repository or its history.** Verified with (1) `rg -I -l` over the working tree and `git grep -I -l -E` over `$(git rev-list --all)` for provider/GitHub/AWS/private-key signatures, and (2) a Python scanner over all 78 git objects, including entries inside historical ZIP blobs. It scanned 541,063 bytes and found zero known credential signatures and zero quoted credential-assignment candidates. Credential-related source/docs were then reviewed by location. This is a signature/manual review, not a mathematical proof against an arbitrarily encoded secret; no actual key value was printed.

## Recommended fixes, ranked

1. Replace the filename `innerHTML` rendering with DOM construction plus `textContent`, and add the malicious-filename regression test. This is the smallest change that closes the clearest clinical-data exfiltration path.
2. Lock Python dependencies (including transitive packages and PyInstaller) with hashes; split read-only build jobs from the write-authorized release job; disable persisted checkout credentials; pin Actions by commit.
3. Move provider credentials into the OS credential store. Until then, enforce restrictive directory/file permissions and atomic writes.
4. Add total-request, file-count, per-file, page, expanded-DOCX, extracted-text, and processing-time limits.
5. Add a per-launch API token and Origin/Host validation to all local API routes while retaining loopback binding and the random port.
6. Treat uploaded text explicitly as untrusted model data and make clinician review/AI provenance unavoidable in the UI and generated report.
7. Verify the downloaded WebView2 bootstrapper by pinned hash or expected Authenticode signer.
8. Sanitize download filenames and replace raw exception responses with safe messages plus credential-free local diagnostics.
9. Add a clear clinical-data transmission/consent notice naming the selected external AI provider.
