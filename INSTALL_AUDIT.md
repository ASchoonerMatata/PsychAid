# PsychAid installation audit

Audit date: 2026-08-25. This was a source-level investigation on Linux; no macOS or Windows execution was possible. “Observed” below means observed in this checkout. Platform UI text and third-party behavior that need native confirmation are kept in the final section.

## Verdict

macOS: **No.** The checked-in `setup.command` is not executable, and, even if the user fixes that, it installs dependencies and then points to a `PsychAid.app` that is absent (`setup.command:21-37`).
Windows: **No, not as a dependable non-technical-user installer.** `setup.bat` has a plausible success path on online x64 Windows 11, but it reports a stale-directory error, builds an unsigned executable on the user's machine, has incomplete download/build checks, and does not ensure the webview runtime (`setup.bat:21-44`, `setup.bat:53-93`; `main.py:55-70`).
The flattened repository no longer matches either installer’s old archive contract: macOS still requires `PsychAid.app/...` (`setup.command:28,34,37`), while both Windows setup implementations still name a `PsychAid` source subdirectory (`setup.bat:53`; `build_setup.py:8-17`).

## macOS — what the user does, step by step

**Works today:** Prerequisites are a real, runnable Python 3 installation with `venv` and pip (not merely the `/usr/bin/python3` CLT shim), internet access, and any native build tooling required if pip cannot obtain wheels. From Terminal in an unmodified checkout, run `cd /path/to/PsychAid && python3 -c 'import sys' && python3 -m venv .venv && .venv/bin/python -m pip install --upgrade pip && .venv/bin/python -m pip install -r requirements.txt && .venv/bin/python main.py`. The macOS dependency resolution and native pywebview launch cannot be verified from Linux.

1. **The user downloads the GitHub source ZIP or clones the repository and double-clicks `setup.command`.** In this checkout, both the filesystem and Git index record `setup.command` as mode `100644`, not executable. The script has a shell shebang (`setup.command:1`) but the repository does not give Finder/Terminal permission to execute it. A Git clone therefore checks it out non-executable; there is no executable bit here for a clone to preserve. A GitHub source ZIP also does not repair a mode that is already `100644`. The first deterministic failure is thus before line 2 runs: the user needs to know to run `chmod +x setup.command` manually. The exact Finder dialog wording needs native confirmation.

2. **If the user manually makes it executable and macOS allows it to open, the script locates itself and rewrites `PATH`.** It prepends `/opt/homebrew/bin`, `/opt/homebrew/sbin`, `/usr/local/bin`, `/usr/bin`, and `/bin`, then appends the prior `PATH` (`setup.command:7-8`). `which python3` therefore chooses the first matching interpreter in that order (`setup.command:10-11`): normally Homebrew on Apple Silicon, a Homebrew/python.org-style install under `/usr/local` on many Intel machines, then `/usr/bin/python3`. This is not a controlled runtime; two users can run different Python and pip versions. If no interpreter is found, the script displays “Python 3 Required” and exits 1 (`setup.command:12-15`). That guard is ineffective on a clean Mac without Command Line Tools: macOS ships `/usr/bin/python3` as a CLT shim, so it exists and makes `which python3` return a non-empty path even when no usable interpreter is installed. Invoking the selected shim at line 16 then triggers the OS developer-tools installation flow or fails instead of running Python, while the surrounding `echo` still emits the success-looking “Python found” line (`setup.command:10-16`). The exact prompt wording and release-specific behavior require a native clean-machine test.

3. **If `/usr/bin/python3` is selected, its exact version cannot be inferred from this repository.** It depends on the installed macOS/Xcode Command Line Tools. A commonly encountered Apple CLT pairing is Python 3.9.6 with pip 21.2.4, but that must be checked on each supported macOS image; it is not a stable macOS API. The installer prints the selected path and version but never prints pip's version (`setup.command:11,16`). pip added `--break-system-packages` in 23.0.1. An older Apple pip rejects line 24 during argument parsing with an error equivalent to `no such option: --break-system-packages`; none of the dependencies on lines 22-23 are then installed (`setup.command:21-24`).

4. **The dependency failure is hidden by shell control flow.** The pip process is piped through two `grep` processes, but the script does not enable `set -e` or `pipefail` (`setup.command:1-24`). Its status is therefore not tested, and line 25 always prints “Dependencies ready” even when pip failed (`setup.command:25`). Even on a compatible pip, there is no virtual environment and no `--user` target (`setup.command:21-24`). A non-writable interpreter normally makes pip fall back to the user site; a user-writable Homebrew prefix may be modified directly. `--break-system-packages` permits modification of a PEP 668-managed interpreter but does not provide isolation or select a consistent target.

5. **A compiler should not normally be necessary on a supported Python/architecture, but this is not guaranteed by the script.** Flask, pypdf, anthropic, python-docx, mammoth, and pywebview are Python-level packages; current compatible ReportLab and PyObjC releases publish macOS wheels, including universal2 wheels covering Apple Silicon and Intel. The explicit PyObjC packages are at `setup.command:22-23`. Because nothing is pinned and the interpreter is uncontrolled, pip may resolve an older compatible release or fall back to a source build; a source build of native packages requires Xcode/Command Line Tools. This wheel-resolution matrix must be tested against the actual minimum Python/macOS versions.

6. **The exact, unconditional application-layout failure is `chmod`.** The flat repository has no `PsychAid.app`, so `chmod +x "$SCRIPT_DIR/PsychAid.app/Contents/MacOS/PsychAid"` targets a nonexistent file (`setup.command:27-28`). `chmod` returns nonzero (normally exit status 1) and prints a “No such file or directory” diagnostic. Because the script does not stop on errors, it immediately prints “App launcher ready” anyway (`setup.command:29`).

7. **The script falsely reports success.** It tells the user twice to double-click `PsychAid.app` (`setup.command:31-37`), but no such bundle exists in the flat checkout. The final `osascript` can succeed, so the overall script can return success even after both pip and `chmod` failed (`setup.command:21-37`). The source entry point that actually starts Flask plus the native webview is `python3 main.py`: the executable path is guarded by `if __name__ == '__main__'`, starts Flask, waits for port 5050, and creates the webview (`main.py:44-64`). `python3 app.py` starts only Flask (`app.py:87-88`). No current macOS script launches either one.

8. **Gatekeeper is a second hurdle, not the first one.** A browser-downloaded ZIP normally carries quarantine metadata, and macOS may refuse or warn on a quarantined script opened from Finder. The exact treatment of a `.command` file varies by macOS release and download/extraction path and needs a native test. If an unsigned, unnotarized `PsychAid.app` were restored, Gatekeeper would normally show an unidentified/developer-verification or malware-check warning and require an explicit override; however, the present repository contains no `.app` to test (`setup.command:28,34,37`). A `git clone` initiated in Terminal commonly avoids browser-download quarantine, but still produces mode `100644` in this repository.

9. **At launch, port 5050 is a fixed, unchecked singleton.** Flask binds `127.0.0.1:5050` (`main.py:7-9`; the direct Flask entry repeats it at `app.py:87-88`). macOS's well-known AirPlay Receiver collision is normally port 5000, not 5050; no standard macOS 5050 conflict was established in this audit. If any process owns 5050, the background Flask thread logs a bind error and dies. The readiness loop can then mistake the unrelated process for PsychAid because it only checks whether `http://127.0.0.1:5050` answers (`main.py:45-53`), after which the webview/browser opens that unrelated service (`main.py:55-67`). If nothing answers, the loop waits about 30 seconds and still attempts to open 5050 (`main.py:48-64`).

## Windows — what the user does, step by step

**Works today:** Prerequisites are an installed CPython 3.11 with the Windows `py` launcher, `venv` and pip, internet access, and WebView2 Runtime for the intended native window. From Command Prompt in an unmodified checkout, run `cd C:\path\to\PsychAid && py -3.11 -c "import sys" && py -3.11 -m venv .venv && .venv\Scripts\python.exe -m pip install --upgrade pip && .venv\Scripts\python.exe -m pip install flask reportlab pypdf anthropic python-docx mammoth pywebview && .venv\Scripts\python.exe main.py`. This source-run path, including dependency installation and native WebView2 behavior, cannot be executed or verified from Linux.

1. **The user downloads/extracts the repository and double-clicks `setup.bat`.** The batch file first changes to its own directory and defines `ROOT`, `python`, and `python.exe` beneath it (`setup.bat:1-8`). This is compatible with the current flat root.

2. **On first run it downloads exactly CPython 3.11.9's amd64 embeddable ZIP.** The URL and architecture are hardcoded (`setup.bat:18-21`). On x64 Windows this provides a private runtime without admin installation. On ARM64 Windows it is not native ARM64: Windows 11 on Arm can normally run it under x64 emulation, producing an x64 build; older Windows-on-Arm environments without x64 emulation cannot. Either way the script never detects architecture or explains the consequence (`setup.bat:21`).

3. **The `_pth` filename is correct for this exact runtime.** CPython 3.11's embeddable archive contains `python311._pth`; uncommenting `import site` is the necessary step that makes `site-packages` visible (`setup.bat:28-33`). The embeddable distribution deliberately omits pip, so the script downloads and runs `get-pip.py` (`setup.bat:35-39`). This can make pip usable after the `_pth` edit. It is nevertheless an unpinned bootstrap: the runtime is fixed at 3.11.9 while `get-pip.py` and all packages float over time (`setup.bat:21,37-44`).

4. **Download error handling is only partial.** `2>nul` hides PowerShell's diagnostic for the Python download, and `if errorlevel 1` checks only the exit code of the `powershell.exe` process (`setup.bat:21-26`). It will catch ordinary terminating `Invoke-WebRequest` failures that make PowerShell return nonzero, but it does not validate that the output is a complete Python ZIP. More decisively, extraction has no status check before deleting the ZIP (`setup.bat:28-30`), the `get-pip.py` download has no status check (`setup.bat:37`), and the get-pip execution is not checked before its input is deleted (`setup.bat:38-39`). The first reliable later check is the package-install command (`setup.bat:44-49`), whose generic message incorrectly reduces every packaging/runtime failure to “Check your internet connection.”

5. **Current PyInstaller can build from embeddable Python; treating this as an unconditional failure would be inaccurate.** The distribution initially lacks pip, but lines 33-38 supply site initialization and pip. PyInstaller added support in 2023 for collecting standard-library `.pyc` files from the embeddable distribution's `python3x.zip`, with a documented basic test on embeddable Python 3.11.4. Since `pyinstaller` is unpinned, a current resolver should install a version with that support (`setup.bat:44`). This remains a nonstandard, untested-in-this-audit toolchain, and application-specific collection can still fail, but there is no source evidence for a guaranteed PyInstaller failure on x64 Windows.

6. **The stale flat-layout `cd` fails visibly, then accidentally leaves the build in the correct directory.** `cd /d "%ROOT%PsychAid"` names a subfolder that no longer exists (`setup.bat:51-53`). `cmd.exe` prints “The system cannot find the path specified.” and returns a nonzero status, but the batch file does not inspect it. Because line 3 already changed into `%ROOT%`, the current directory remains the flat repository root. That is where `main.py`, `templates`, and `static` now live, so the following PyInstaller command's relative paths are accidentally correct (`setup.bat:3,53-80`). This is a real layout mismatch and confusing error, but not by itself a deterministic build blocker for `setup.bat`.

7. **The alternate Python installer, `build_setup.py`, does fail deterministically on the flat layout.** It constructs `<repo>/PsychAid`, requires it to be a directory, and exits 1 when it is absent (`build_setup.py:8-15`). Its subsequent dependency installation and build are unreachable (`build_setup.py:17-71`). This script is not called by `setup.bat`; it is a separate, currently broken setup path.

8. **The primary PyInstaller command is structurally appropriate for a one-file build.** It bundles `templates` and `static`, collects webview data, names hidden imports, and uses `main.py` (`setup.bat:55-80`). In a successful one-file build the result path checked by `if exist "dist\PsychAid.exe"` is correct, and it is copied beside the setup script (`setup.bat:82-89`). There is no onedir fallback in `setup.bat` itself.

9. **`build_setup.py`'s fallback command surgery is odd but well formed.** The comprehension removes `--onefile`; its `replace` is consequently a no-op, and the next line inserts exactly one `--onedir` after `--windowed` (`build_setup.py:73-78`). The resulting command contains one mode flag and is valid. The post-build path is wrong for that fallback: onedir puts the executable at `dist\PsychAid\PsychAid.exe`, but the script only looks for `dist\PsychAid.exe` (`build_setup.py:80-85`). A successful fallback is therefore reported as “Could not find PsychAid.exe” (`build_setup.py:93-95`). The analogous check in `setup.bat:82` is not affected because that file never attempts onedir.

10. **`pip install pywebview` supplies pywebview's default Python dependencies, including the Windows `pythonnet` path, but it cannot guarantee the external browser runtime.** The package is installed at `setup.bat:44`/`build_setup.py:22-27`. pywebview documents pythonnet with .NET >4.0 and WebView2 Runtime for the current Chromium backend. WebView2 Runtime is included with Windows 11 and present on the vast majority of Windows 10 devices, but not every Windows 10 device; Microsoft recommends detecting/installing it. Neither setup implementation checks or deploys it (`setup.bat:41-49`; `build_setup.py:20-34`). If webview import/startup raises, `main.py` catches every exception without printing it and opens the default browser at localhost instead (`main.py:55-70`). Thus an end user may simply see a browser rather than a native window, with no explanation. The fallback still provides most web UI, but `window.pywebview.api` native-dialog behavior is unavailable (`main.py:12-41`).

11. **The produced executable has no signing or reputation step.** The build requests `--onefile --windowed` (`setup.bat:55-58`; `build_setup.py:42-46`) and then tells the user to double-click the result (`setup.bat:82-89`; `build_setup.py:84-90`). No code-signing command or installer packaging exists. Whether SmartScreen displays “Windows protected your PC” depends on Mark-of-the-Web and reputation; whether Defender or another antivirus flags the PyInstaller one-file bootloader/extraction pattern depends on product/signature versions. Both are realistic distribution risks, but neither exact result can be proven from Linux or from these sources alone.

Dependency-list detail:

- `requirements.txt:1-9` and `setup.command:21-24` contain the same nine runtime names: `flask`, `reportlab`, `pypdf`, `anthropic`, `python-docx`, `mammoth`, `pywebview`, `pyobjc`, and `pyobjc-framework-WebKit`.
- `setup.bat:44` and `build_setup.py:22-27` contain the same Windows/build list: the first seven cross-platform runtime names above plus `pyinstaller`; they omit `pyobjc` and `pyobjc-framework-WebKit`.
- Therefore there are four duplicated declarations but **two** currently distinct package sets, not three distinct sets. The drift is that Windows adds a build-time dependency while macOS/requirements add two macOS dependencies. No declaration pins even one package version (`requirements.txt:1-9`; `setup.command:21-24`; `setup.bat:44`; `build_setup.py:22-27`). The embedded CPython download alone is version-fixed (`setup.bat:21`).

Runtime data/security detail:

- `database.py` chooses `%APPDATA%\PsychAid` on Windows and `~/Library/Application Support/PsychAid` on macOS (`database.py:2-7`). If `APPDATA` were absent, its Windows fallback is the literal unexpanded `~` (`database.py:4`), unlike `report_generator.py`'s expanded-home fallback (`report_generator.py:5-6`). In normal Windows desktop sessions `APPDATA` is expected to exist.
- The API configuration is `%APPDATA%\PsychAid\config.json` on Windows and `~/Library/Application Support/PsychAid/config.json` on macOS (`report_generator.py:3-11`). Those normal-case roots are consistent with `database.py`, although `database.py` is unused.
- `save_config` creates the directory and writes ordinary JSON with `open(..., 'w')` (`report_generator.py:20-24`). On macOS it does not request mode `0600`; a new file normally follows the user's umask and may commonly be `0644`. On Windows it inherits directory ACLs. Neither is encryption, Keychain, or Credential Manager. The key is posted by the settings UI and inserted back into the password input (`templates/settings.html:14-16,28-38`; `app.py:28-39`).
- The hardcoded Flask key signs Flask session/cookie state; it is not the Anthropic key (`app.py:14` versus `report_generator.py:57-59`). No current route uses Flask `session` (`app.py:20-85`), so describing this literal as remote-code execution or API-key exposure would be inaccurate. Loopback binding narrows exposure (`main.py:9`; `app.py:88`), though other processes/pages on the same host remain the relevant trust boundary.

Frozen/source detail:

- Source mode sets `app.BASE_DIR` to the directory containing `app.py`; frozen mode uses PyInstaller's extraction directory, `sys._MEIPASS` (`app.py:3-6`). Flask's template/static paths are based on that value (`app.py:11-13`). Both Windows build commands explicitly add those directories (`setup.bat:59-60`; `build_setup.py:47-49`).
- `main.py` does not branch on `sys.frozen`; it derives `BASE_DIR` from `__file__` and inserts it in `sys.path` (`main.py:1-5`). Under modern PyInstaller, bundled `__file__` resolves inside the bundle/extraction directory, so imports are expected to remain bundle-local. In source mode it is simply the repository root.
- User configuration is intentionally outside `BASE_DIR`/`_MEIPASS`, so it survives a one-file restart (`report_generator.py:3-24`). `database.py` similarly computes a per-user location but is unused (`database.py:1-8`).

## Recommended fixes

1. **Choose strategy (a): plain “run from source” scripts for the next working release.** This is the smallest credible repair. PsychAid is already a local Flask/pywebview Python application (`main.py:44-64`); source launchers avoid building an unsigned executable on each user's machine, restoring a fake `.app` layout, and immediately taking on Apple Developer ID signing/notarization plus Windows code-signing/reputation infrastructure. Prebuilt signed binaries—strategy (b)—are the better eventual consumer product, but only after CI builds, native testing, signing, notarization, update/release ownership, and architecture coverage exist. An unsigned locally generated one-file binary is the worst midpoint (`setup.bat:55-89`).

2. **Add a short README before deeper installer work.** State the supported per-OS prerequisites and exact source-run steps, identify `setup.command` and `setup.bat` as the intended user entry points once repaired, classify `build_setup.py` as developer-only or retire it, and explain what the user should launch after setup. This is the cheapest way to remove the current zero-documentation start, although it does not replace the installer repairs.

3. **Make the macOS script executable and make it a real source launcher.** Change the Git mode of `setup.command` from `100644` to `100755`. In `setup.command`, stop on errors, validate the selected interpreter by running `"$PYTHON3" -c 'import sys'` and checking its exit status rather than trusting `which`, create a repository-local `.venv`, install from the single requirements file, and run `.venv/bin/python main.py`. Remove the nonexistent `PsychAid.app` `chmod` and both success messages (`setup.command:10-37`). This fixes all deterministic macOS blockers with one script plus a mode change.

4. **Make the Windows script operate explicitly in the flat root and run source.** Remove `cd /d "%ROOT%PsychAid"` and use `%ROOT%` (`setup.bat:53`). Prefer a detected supported system Python (`py -3.11`/`python`) plus `%ROOT%.venv` over the embeddable distribution; create the venv, install the shared requirements, and run `main.py`. If keeping embedded Python temporarily, pin/checksum both bootstrap inputs, check every command, detect CPU architecture, and give specific errors (`setup.bat:18-49`).

5. **Consolidate dependencies.** Make `requirements.txt` the only runtime list and call `pip install -r requirements.txt` from both setup scripts. Use environment markers for macOS-only PyObjC packages. Keep PyInstaller out of runtime requirements; if binary builds return later, put it in a separate pinned build requirements file. This removes duplication at `setup.command:21-24`, `setup.bat:44`, and `build_setup.py:22-27`.

6. **Pin and test a support matrix.** Select a minimum/current Python pair and pin or lock compatible package versions for macOS Intel, macOS Apple Silicon, Windows x64, and (if supported) Windows ARM64. Confirm wheel availability so setup never unexpectedly compiles PyObjC/ReportLab. Remove `--break-system-packages`; a venv makes it unnecessary (`setup.command:21-24`).

7. **Fail clearly and launch only after verification.** In shell, enable failure propagation and test imports before printing success (`setup.command:21-37`). In batch, check download, extraction, get-pip/venv creation, package installation, and launch separately (`setup.bat:21-49`). Do not reduce every nonzero package result to an internet error (`setup.bat:45-48`; `build_setup.py:30-33`).

8. **Handle the webview backend explicitly.** On Windows, test for WebView2 and either install Microsoft's Evergreen bootstrapper or state that browser mode is supported. Log/display the exception currently swallowed at `main.py:55-67`. If browser mode is accepted, make its missing native save-dialog behavior explicit (`main.py:12-41`).

9. **Remove the fixed-port race.** Bind an available loopback port (for example, ask the OS for port 0 and pass the chosen port to the readiness check/window) or preflight 5050 and exit with a visible message. Ensure the readiness response identifies PsychAid rather than accepting any HTTP server (`main.py:7-9,47-67`).

10. **Restrict API-key storage with platform-native lazy choices.** At minimum, create the macOS config with user-only permissions and document the Windows inherited-ACL behavior (`report_generator.py:20-24`). Prefer Keychain/Credential Manager only when the added integration is justified. Do not spend time rotating `app.secret_key` before sessions are introduced; remove session support or generate a per-install key when it becomes relevant (`app.py:14`).

11. **Retire or repair `build_setup.py`.** Under the recommended source strategy, delete it from the user install path. If retained for developer builds, point `src_dir` at `script_dir` (`build_setup.py:8-17`) and, after onedir fallback, copy/publish the `dist/PsychAid/` directory rather than checking only `dist/PsychAid.exe` (`build_setup.py:73-95`).

12. **If strategy (b) is later adopted, ship prebuilt native artifacts rather than compiling on the user's PC.** Build x64/ARM64 as supported, sign Windows artifacts, sign and notarize the macOS app, staple notarization, test clean-machine Gatekeeper/SmartScreen flows, and publish checksums. This is larger than the source-script repair but is the route to a genuinely double-click consumer install.

## Uncertain / needs a real machine to confirm

- The exact Finder/Terminal message when the current non-executable `setup.command` is double-clicked on each supported macOS release. The mode problem itself was observed (`100644`); only UI wording is uncertain.
- The exact developer-tools installation prompt, failure text, and per-release behavior when `/usr/bin/python3` is invoked without Command Line Tools. Source inspection establishes that the shim's filesystem presence bypasses the empty-path guard (`setup.command:10-16`), but the resulting macOS UI and process transcript cannot be captured from Linux.
- Whether a GitHub browser ZIP's quarantine metadata reaches `setup.command` after the user's particular browser/archive utility, and the exact Gatekeeper prompt after manually adding execute permission. Apple documents overriding blocked unidentified apps, but `.command` handling must be tested separately from `.app` handling.
- The exact `/usr/bin/python3` and pip versions on every supported macOS/Xcode CLT combination. The repository makes no version contract (`setup.command:8-16`). A matrix should record `which python3`, `python3 --version`, and `python3 -m pip --version`; the often-seen 3.9.6/21.2.4 pairing is not asserted as universal.
- The exact dependency versions selected today by each possible macOS interpreter. The declarations are unpinned (`requirements.txt:1-9`; `setup.command:21-24`), and index state changes. Clean Intel and Apple Silicon tests should prove whether all artifacts are wheels and whether a compiler is ever invoked.
- The exact stderr and final script exit status for pip failure plus the two `grep` filters on macOS. Source analysis proves the pip status is not inspected and execution continues (`setup.command:21-37`); a native transcript should capture presentation details.
- Gatekeeper's exact text for a restored unsigned/unnotarized `.app`. There is no current app bundle to submit to `codesign`, `spctl`, or `stapler` (`setup.command:28,34,37`).
- A full Windows x64 build using the downloaded 3.11.9 embeddable runtime and the package versions resolved on the test date. Current PyInstaller has embeddable-Python support, but this application's complete hidden-import/webview bundle was not built on Windows (`setup.bat:41-80`).
- A Windows ARM64 run: whether the target Windows release has x64 emulation enabled, whether every selected amd64 wheel loads, performance, and whether an x64 PyInstaller output is acceptable (`setup.bat:21,44`).
- PowerShell exit codes for DNS failure, TLS/proxy interception, HTTP error, partial response, and corrupt ZIP. Source analysis shows only the first process exit is checked and later steps are unchecked (`setup.bat:21-39`); it does not justify one universal failure transcript.
- pywebview behavior on clean Windows 10 without WebView2, on Windows 11, and under PyInstaller onefile. Source analysis proves exceptions are swallowed into browser fallback (`main.py:55-70`); the precise backend choice/error depends on installed runtimes.
- SmartScreen and Defender outcomes for `PsychAid.exe`. Signing is absent (`setup.bat:55-89`; `build_setup.py:42-90`), but warnings/quarantine/false positives depend on Mark-of-the-Web, prevalence/reputation, Defender definitions, and third-party antivirus. A clean VM and submitted release artifact are required.
- Port-5050 behavior with a real macOS/Windows conflicting listener, including what pywebview renders. The code can mistake any HTTP response for readiness (`main.py:47-67`), but service-specific UI is not predictable from Linux.
- Actual config-file permissions/ACLs under supported user account policies. The code requests no explicit mode (`report_generator.py:20-24`); macOS umask and Windows inherited ACLs must be recorded on native machines.
